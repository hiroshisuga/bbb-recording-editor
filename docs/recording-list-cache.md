# 録画一覧のサマリーキャッシュ

一覧APIが参照のたびに全会議のXMLを読み込み・ハッシュ計算・解析する処理を、ファイル属性で検証するプロセス内サマリーキャッシュに変更した。既存の音声・波形プレビュー用ディスクキャッシュとは独立している。

## 保存先と内容

`Repository` が所有する `ListCache` に、一覧用の会議名、開始日時、会議時間、録画区間の有無・合計時間、警告と、`metadata.xml` の解析結果だけを保存する。XML本文・Nokogiri DOM・メディア・会議詳細レスポンスは保持しない。

サービス起動時に作られたRepositoryはHTTPリクエスト間で共有される。タブやブラウザーを閉じても同じ `bbb-recording-editor` プロセスが動いていればキャッシュは残り、サービス再起動後は空になる。複数プロセス構成ではキャッシュもプロセスごとになる。設定変更や追加の依存ライブラリは不要。

全件走査で自分のキャッシュを追い出す問題を避けるため、会議数固定の小容量LRUは使わない。列挙された会議すべての軽量サマリーを保持し、一覧から消えた会議は次の一覧取得で整理する。保持量は会議数・名前・警告などの長さに比例し、固定のメモリ上限は設けていない。

## 更新と安全性

- rawサマリーは `events.xml`、`saved.json`、`original-events.xml` の状態を参照する。メタデータは公開・非公開・処理中の保存先ごとに識別する。
- 属性には解決済みパス、device/inode、mode、uid/gid、サイズ、mtime/ctimeの精密な時刻を使う。ヒット確認でXML本文を読み直したりチェックサムを計算したりしない。
- 読み込み前後で属性が変わった結果や、解析・参照に失敗した結果は保存しない。ファイル全体のトランザクションを導入するものではなく、読み込み中に変更された場合、そのリクエストには通常の読み取り時点の結果を返し、次回に再解析する。
- ファイル属性・パスの検証はヒット時にも行う。シンボリックリンクの範囲検証も継続する。raw保存・初期化・削除の成功時には、該当会議を明示的に無効にする。
- 公開・非公開・処理中のディレクトリ配置、完了／失敗マーカー、再構築依頼・タイトル復元の状態、rawの存在確認はキャッシュしない。XMLがないrawの下位ディレクトリ探索も毎回実行する。
- 削除確認は `list(cache: false)` でサマリーキャッシュを回避する。会議詳細や保存・初期化・再構築の検証も現在のファイルを読み込む。一覧内では取得済みの公開状態を再構築情報の組み立てに渡し、同じメタデータの重複解析を減らす。
- 同じ入力の並行取得はキー単位で待ち合わせ、異なる会議のXML解析はグローバルなキャッシュロックの外で行う。使用後の待ち合わせロックは破棄する。返す名前・警告やキーの文字列を呼び出し元と共有しない。

通常再生や一覧のブラウザー内フィルター変更は、もともと一覧APIを呼ばない。今回の対象は、ページを開いた時、一覧更新、保存・初期化後、再構築中の5秒ごとの一覧再取得など。メディア解析・初回プレビュー生成・全件のファイル属性確認・一覧の組み立ては引き続き必要になる。

## 測定

Ruby 3.3.8、Linux x86_64、ローカル一時ファイルの合成300会議を使用した。各会議に1,001イベントと非公開メタデータを置き、raw XMLの合計は35,712,600バイト。キャッシュ無効の経路を5回、初回生成を1回、取得済みキャッシュを5回測った。比較は**この変更内のキャッシュ無効・有効の経路**であり、旧コミットとの別プロセス比較ではない。

| 条件 | 所要時間 | XML解析回数／取得 |
| --- | ---: | ---: |
| キャッシュ無効、5回の中央値 | 2,547.3 ms | 600 |
| キャッシュ初回生成、1回 | 2,922.9 ms | 600 |
| キャッシュ取得済み、5回の中央値 | 55.4 ms | 0 |
| 1会議のraw変更後、1回 | 59.0 ms | 1 |

初回は解析とキャッシュ作成が必要で、高速化するのは主に再取得。ファイル一覧・属性の取得も測定に含む。HTTP通信、ブラウザーの描画、映像・音声処理、BBB本番環境は含まない。OSのファイルキャッシュはリセットしておらず、実環境で同じ所要時間・改善率を保証しない。

300会議・600エントリーの保持グラフ（キー、属性、値）を `ObjectSpace.memsize_of` で再帰的に概算すると640,792バイト（約0.61 MiB）だった。Ruby VM全体のRSS・アロケーターの余剰領域・解析中の一時DOMを含むメモリ上限ではない。

測定値は [recording-list-results.json](recording-list-results.json) に保存した。

```bash
ruby scripts/benchmark-recording-list.rb \
  --meetings 300 --events 1000 --iterations 5 \
  --output work/recording-list-results.json
```

アプリと同じRuby／Nokogiriで実行する。一時録画は終了時に削除され、出力JSONだけが指定先に残る。実際のBBBデータにはアクセスしない。

## 検証

テストでは、キャッシュ取得時のXML読み込み・解析・ハッシュ計算の省略、同サイズ／mtime保持の更新、atomic rename、編集履歴・元XMLの変更、公開先移動、失敗マーカー・完了状態、権限エラーと回復、パス逸脱、raw下位ファイルの追加、保存・初期化、300会議の繰り返し走査、削除された会議の整理を確認する。

独立したHTTP接続間の共有、Repository再生成時の空状態、返却データやキーの変更からの隔離、並行取得の待ち合わせ、削除確認のキャッシュ回避も検証する。

```bash
ruby -Ieditor/test -e 'Dir["./editor/test/*_test.rb"].sort.each { |file| require_relative file }'
```
