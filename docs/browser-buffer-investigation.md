# ブラウザの先読みが数秒に見える理由の調査

2026-10-31。PR #40マージ後の調査。調査結果に基づくアプリの修正も含む。

**`video.buffered` が数秒でも、受信済みの動画が数秒分しかないとは限らない。** 可変ビットレート動画と長さ情報がないWebMで、この違いを実際のChromiumで再現した。

## 添付ログから確認できること

新しいログでは482件・約126秒が記録され、高速追随の開始は0回。シーク完了時の遅れは約7.7秒、7.4秒、3.8秒であり、高速追随の開始条件の8秒にも届いていない。通常補正が可能な時点で、遅れ8秒以上と先読み24秒以上が同時に成立する記録もない。

先読みが2〜8秒程度でも、通信取得中ではない `networkState=1` と、再生準備が十分な `readyState=4` が同時に記録される。一方、別の位置では先読みが100秒を超える。これは全区間で一定の秒数に制限されているという挙動ではない。

これだけで実際の録画の受信済みバイト範囲・正確なキャッシュ保持量までは分からない。この時点の診断ログには `video.duration` やHTTPの受信バイト範囲が含まれていないため、下記の機構が実際の素材にどの程度影響しているかは確定していない。

## Chromiumのコードで確認した構造

1. `MultiBufferDataSource` はHTTPから受け取ったバイトを保持し、推定ビットレートや再生速度などから先読み量を決める。十分と判断すれば取得を休止する。アプリの `preload="auto"` は全ファイルの取得や、特定の秒数の先読みを保証する指定ではない。
2. その先の `FFmpegDemuxerStream` は、解析した圧縮パケットを基本的に約2秒分キューへ入れる。デコーダーなどの分も含めると、解析済み時間範囲が現在位置の数秒先までになることがある。ここで使われるFFmpegはブラウザ内部のライブラリであり、BBBサーバで実行するFFmpegプロセスではない。
3. `WebMediaPlayerImpl::Buffered()` は、この解析済み時間範囲に、受信バイト位置から推定した時間範囲を追加する。ただし全体時間が `Infinity` なら後者を追加しない。
4. バイト位置の時間換算は、おおむね **バイト位置 ÷ ファイル総バイト数 × 全体時間**。部分ごとにデータ量が大きく異なる動画では、この推定位置と実際の映像時刻がずれる。推定範囲が現在位置より前に出てしまうと、現在位置を含む範囲としては解析済みの数秒分しか見えない。

したがって、次の3つは区別する必要がある。

| 層 | 確認するもの |
| --- | --- |
| HTTP・内部キャッシュ | どのファイル位置のバイトが受信されたか。受信履歴と、現在も保持されている範囲も厳密には別 |
| 動画の解析 | 受信したバイトから、どの映像時刻までパケットを取り出したか |
| 画面への表示 | 実際にどの時刻のフレームが描画用に提出されたか |

リポジトリの配信処理 `editor/server.rb` はバイトRangeを受け付け、要求された範囲を末尾まで配信する。64KiBずつ書き込むが、再生時間を数秒へ制限する処理はない。実サーバ固有の設定・転送性能については、このソース確認だけで断定しない。

## 再現実験

Linuxのheadless Chromium 131.0.6778.204、ローカルHTTP Rangeサーバ、合成VP8動画を使用。受信量はDevTools Protocolのネットワークイベント、パケットの実際の時刻は `ffprobe` のファイル位置・サイズ・PTSから調べた。元の会議動画は使用していない。

| 条件 | 120秒地点での先読み表示 | 実際の受信・再生 |
| --- | --- | --- |
| 比較的均一なデータ量、長さ情報あり | 数十秒以上 | バイト位置からの時間推定も比較的近い |
| 前半はほぼ静止、後半は動きが多い動画、長さ240秒 | 2.5秒 | 再測定では約202〜205秒地点までのパケットを受信済み |
| 同じ動画を全取得後、Blob URLで再生 | 120秒 | `buffered` は全体の0〜240秒になる |
| 長さ情報がないWebM（`duration=Infinity`） | 2.5秒 | 受信済みバイトの時刻推定を表示へ加えない |

さらに、可変ビットレート動画と `duration=Infinity` の動画で、120秒地点まで移動してから通信をオフラインに切り替え、4倍速で約12秒間再生した。

- 可変ビットレート動画は120秒から約168.0秒へ進んだ。
- 長さ情報がない動画も120秒から約168.3秒へ進んだ。
- どちらも切り替え時の先読み表示は2.5秒で、再生後も現在位置から約2.5秒の表示が続いた。

**通信を切っても約48秒分進めたため、先読み表示の2.5秒を「あと2.5秒で受信データを使い果たす」という意味には使えない。** 詳細の要約は [browser-buffer-results.json](browser-buffer-results.json)。

## 高速追随への影響

PR #40の実験は、デコード・速度制御を切り分けるため、全取得した動画をBlob URLで再生していた。この条件では先読み表示が大きくなり、HTTP配信で発生する上記の差を捉えられていなかった。

PR #40では開始条件の24秒だけでなく、通常補正にも「先読み秒数 ÷ 2」を速度の上限として使っていた。この秒数が実際の受信済み範囲を過小評価する場合、開始・増速・減速のすべてが過剰に慎重になる可能性がある。

## 追加の実機情報

MacのBraveから取得したMediaパネルの3ファイルは、同じプレーヤーの累積記録だった。動画はVP8・1920×1080・長さ9958.972秒で、VideoToolboxではこの構成を扱えず `VpxVideoDecoder` が選ばれている。デコーダー選択のメッセージは情報レベルで、致命的なエラーは0件。ソフトウェアで処理するため、速い設定を常用できるという前提にはしない。

シーク後に映像バッファーが準備完了へ戻るまで約13.2秒、約5.4秒かかる場面があった。理由付きで記録された通常再生中の `DEMUXER_UNDERFLOW` は約17ミリ秒の1回で、この記録から常時の回線不足とは判断しない。メッセージの再生速度ログは途中で抑制されるため、そこから全期間の最高速度も断定しない。この情報に受信バイト範囲はなく、実録画のキャッシュ保持量が確定したわけではない。

## アプリの修正

- 画面共有は遅れ3秒以上・再生可能・タブ表示中なら計測を始める。開始前の報告バッファー24秒以上という必須条件を外す。
- 通常補正を約2秒測定し、直近の速度を超える小さい段階から試す。候補は0.75・1・1.25・1.5・2・3・4・6・8・12倍速。例えば音声1倍速で通常補正が1.25倍速なら、次は1.5倍速を試し、確認できた場合だけ2倍速へ進む。基準が指定速度と同じ場合も、その速度で映像が進むなら小さい増速を試せる。
- 報告バッファーが数秒という理由だけでは、試行を拒否・中断しない。内部時計と表示フレームの実際の進み、遅れの縮まり方、待機時間で評価する。約2秒ごとの比較、進み8%超・回復速度0.15秒/秒超の改善、30秒の再増速制限は維持する。
- 通常補正の基準自体が不調なら、指定速度へ戻して30秒間は増速を抑える。実際の待機・準備不足では直ちに指定速度へ戻し、200ミリ秒超の待機や観測区間の10%以上の待機では高速探索をやり直す。再開後は直ちに高速度へ戻さず、通常補正から計測する。
- 小さい遅れの通常補正にも、確認済みの速度を上限として利用する。実測があるのに `buffered / 2` だけで遅い補正を続けることを防ぐ。追いつく直前は通常補正へ戻し、同じ回復の途中で探索を何度もやり直さない。
- 一時停止・手動シーク・素材変更・音声速度変更で計測をリセットする。フレーム通知不足、API非対応、高速度を拒否するブラウザへの退避も維持する。
- UIを「バッファー（ブラウザ報告）」へ改め、確実に再生できる残り時間ではないことを説明する。診断ログに全体時間・解像度・確認済み速度を加え、`durationchange` と `suspend` も記録する。
- 音声の再生・速度・位置には介入しない。既存の警告条件は変えず、自動補正シーク・追加取得・再エンコードも追加しない。ウェブカムは従来の補正を維持する。

報告値を参考にする通常補正と、実測のある画面共有の補正を区別する。これは受信量を新しく正確に測れるようにした変更ではなく、報告値だけでは実際のキャッシュ量を判断できないことに対応する変更である。

## 短い映像待ちの後の補正

追加の実機ログでは新しい追随が最大4倍速まで動作した。一方、3倍速の進みを確認して4倍速を試した直後に約11ミリ秒の待機が起こり、確認済み速度が消えた。その後、残り約2.4秒を縮めるのに約12秒かかっていた。

待機中は指定速度へ即座に戻す方針を維持する。200ミリ秒以内の待機では、確認済み速度を使用不能な候補として一時保留する。再開時に試行中だった高速度へは戻さず、通常補正の速度で新しい約2秒の観測を始め、時計と表示フレームが順調に進むことを確認してから候補を復帰させる。残り3秒未満の仕上げでもこの再確認を許す。観測開始時の250ミリ秒を除外し、フレーム時刻の比較区間500ミリ秒以上、設定速度の70%以上の実効速度、増速中は毎秒0.1秒超の遅れ回復という既存の確認条件を使う。確認成功は診断イベント `catch-up-revalidated` に記録する。

長い待機、再確認中の再待機、進みの不足、フレーム通知不足、非表示化、シーク・一時停止・素材変更・音声速度変更では保留した速度を再利用しない。通知が不足する場合は従来通り最大3.5秒で観測を打ち切る。保持する候補は直前に確認できた速度だけで、未確認の試行速度は含めない。音声、動画のシーク、配信、rawファイルには変更を加えない。

この変更は210テスト・17スイートと本番ビルドで確認した。短い待機後の再確認、残り3秒未満の補正、音声2倍速、遅いフレーム・フレーム通知不足・再待機・長い待機時の破棄、状態リセット、実際のコンポーネントに対するメディアイベントの接続を検査する。LinuxのChromium 131でもHTTP配信の合成VP8動画と独立した音声を使い、報告範囲を2.5秒に固定し11ミリ秒後に再開イベントを送る試験で `catch-up-revalidated` を確認した。音声の停止・速度変更と補正シークは0回。これは短い待機を模した試験で、実際の通信不足を再現したものではない。自然に起きる追加の映像待ちなどで所要時間は変わるため、実録画での短縮量を保証しない。

## 修正後のHTTP配信での確認

実際のReact `VideoPreview` をChromium 131で動かし、動画はローカルHTTP Range配信、音声は別のネイティブ音声要素で再生した。動画を全取得したBlobへ置き換えてはいない。以下は合成素材での結果であり、元の会議動画・MacのBraveでの改善量を保証するものではない。

| 条件 | 結果 |
| --- | --- |
| 可変ビットレート・音声1倍速・初期遅れ60秒、準備後はオフライン | PR #40は20秒後も約55.6秒遅れ。修正後は最大12倍速まで段階的に上がり約20.7秒で追いついた。計測開始時の報告バッファーは2.5秒 |
| 長さ情報なし・音声1倍速・初期遅れ60秒 | 最大12倍速、約20.7秒で追いついた |
| 可変ビットレート・音声2倍速・初期遅れ30秒 | 最大8倍速、約12.6秒で追いついた |
| 可変ビットレート・初期遅れ7.5秒 | 最大3倍速、約10.1秒で追いついた。旧開始条件の8秒未満でも計測できた |
| 1080p・30fps・先頭にのみキーフレーム、初期遅れ20秒 | 最大6倍速、約9.0秒で追いついた |
| 転送を32KiB/秒・遅延30msへ制限 | 映像待機8回。最高1.1倍速から指定の1倍速へ戻し、増速を制限。20秒後の映像遅れは約16.0秒で、通信不足自体を解消する処理ではない |

追いついた判定は、内部時計の差0.15秒以内・フレーム時刻との差0.3秒以内・指定速度への復帰を750ミリ秒以上保った時点。7条件すべてで音声要素の停止・速度変更と、映像の補正シークは0回だった。詳細は [progress-based-http-results.json](progress-based-http-results.json)。通常素材・開始時刻が600秒ずれた素材・長さ情報なしの素材で、描画フレームの更新と一時停止中のシークも確認した。日本語の診断表示は幅380pxで折り返して表示される。

Jestの199テスト・17スイートと本番ビルドが成功。報告バッファーが2.5秒のままの増速、実際の進み不足・待機時の減速、再試行制限、表示フレーム通知不足、ブラウザによる速度拒否、音声2倍速、通常の細かな補正への復帰を検査している。

## 再現方法

Playwrightを別途インストールし、`ffmpeg` / `ffprobe` を使用する。新しく作るテストファイルだけを指定し、会議のraw素材は上書きしない。

```bash
ffmpeg -f lavfi -i testsrc2=size=640x360:rate=10 -t 240 \
  -c:v libvpx -deadline realtime -cpu-used 8 -b:v 400k -g 100 /tmp/buffer-finite.webm

ffmpeg -i /tmp/buffer-finite.webm -c copy -live 1 /tmp/buffer-live.webm

ffmpeg -f lavfi -i color=c=navy:size=640x360:rate=10:duration=180 \
  -f lavfi -i testsrc2=size=640x360:rate=10:duration=60 \
  -filter_complex '[0:v][1:v]concat=n=2:v=1:a=0[v]' -map '[v]' \
  -c:v libvpx -deadline realtime -cpu-used 8 -b:v 1000k -g 300 /tmp/buffer-vbr.webm

node scripts/benchmark-buffer-reporting.cjs \
  --finite /tmp/buffer-finite.webm --live /tmp/buffer-live.webm --vbr /tmp/buffer-vbr.webm \
  --browser CHROMIUM_EXECUTABLE --playwright PLAYWRIGHT_MODULE_PATH \
  --output /tmp/buffer-reporting-results.json
```

HTTP、Blob、オフラインの各条件を順番に試す。オフライン試験では、表示上の先読みが少なくても40秒を超える素材時間を進めることを検査する。受信履歴だけではキャッシュの保持を保証できないため、このオフライン再生で実際に使えることも確認する。ブラウザ・生成素材・負荷により数値は変わる。
