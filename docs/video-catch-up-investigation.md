# 4倍速を超える映像追随の調査

2026-10-31。対象コード: `afe458c128f3d65510e24b2974ccad4d57245da8`（PR #39マージ後）。

**十分に先読みされた動画では、再シークせずに4倍速を超えて追いつく余地がある。ただし、速度設定を上げすぎると、実際の映像の進みが遅くなる場合も確認できた。** 次の実装では、バッファ量だけでなく増速前後の実測結果に基づく試行・取り消しが必要。

この変更で追加するのは調査用スクリプトと資料。アプリの速度制御、警告条件、raw素材、配信・再エンコード処理は変更しない。

## 現行制御で確認した制限

- `src/components/recording-editor/videoSync.js` は動画の絶対速度を4倍速に制限する。
- それとは別に、音声の指定速度に対する増速幅は最大3倍。このため、音声が1倍速なら映像は最大3倍速、音声が2倍速なら絶対上限の4倍速になる。
- 再生中の同期には速度だけを使い、自動補正シークは行わない。初期位置合わせ、手動シーク、一時停止中の位置合わせは別。
- 音声1倍速・映像3倍速なら、60秒の遅れを減らす理想的な速度は実時間1秒につき2秒。最低でも約30秒かかり、末尾の減速分も加わる。

## 計測方法

`scripts/benchmark-video-catch-up.cjs` で、実際のChromiumの `<video>` と独立した `<audio>` を再生した。音声はローカル生成した無音WAVで、メディア時計はブラウザの実物を使う。

- 動画ファイルをローカルHTTPから最後まで取得し、Blob URLとして再生。`video.buffered` の現在位置から末尾までの連続範囲も確認し、通信待ちの影響を切り離す。
- 測定開始前に動画を20秒へ移動。初期シークの所要時間は追随時間に含めない。
- 固定速度の比較では、3・4・8・12・16倍速を各4秒再生する。32倍速はAPIの受付可否も確認する。
- `requestVideoFrameCallback` が返すフレームの `mediaTime` の増分を、通知の実時間の増分で割る。最初の500ミリ秒はこの速度計算から除外する。単に `video.currentTime` が進むだけの状態と区別するためである。
- 音声と動画の内部時計の差、最新フレームの時刻差、フレーム通知からの経過時間、先読み、`waiting`、欠落フレーム、音声の実際の進みも記録する。
- 回復試験は現行の `synchronizationRate` を読み込み、100ミリ秒ごとに適用する。比較用の `fast8` / `fast12` / `fast16` は、遅れが2秒より大きい間だけ上限を引き上げ、先読みを少なくとも実時間2秒分残す。2秒以下になったら現行制御に戻す。これは上限比較用の実験であり、実測による速度の学習・退避はまだ実装していない。
- 回復判定は内部時計の差が0.15秒以内、最新フレームとの差が0.3秒以内、映像の速度が音声の指定速度に戻った状態が750ミリ秒続くこと。その区間の開始時刻を回復時間として報告する。
- 測定中に音声の停止・速度変更、動画のシークが発生しないことをスクリプト内で検査する。テストの準備・終了時の操作は対象外。

環境はLinuxのheadless Chromium **131.0.6778.204**。合成VP8動画2種類を使い、いずれもキーフレームは冒頭の1個だけである。

| 動画 | 長さ | 解像度・フレームレート |
| --- | --- | --- |
| 軽いテスト動画 | 240秒 | 640×360、10fps |
| 高解像度テスト動画 | 120秒 | 1920×1080、30fps |

これはコンポーネント全体・BBBサーバ・実際の録画に対する試験ではなく、現行の純粋な速度計算とネイティブ再生経路を使う実験である。実際の素材、ブラウザ、デコーダー、端末、同時再生するカメラ数によって限界は変わる。

## 結果

### 固定速度での実際のフレームの進み

「実測速度」はフレームの素材内時刻が実時間1秒で何秒進んだか。先読みの値は読み込み済み圧縮データの時間であり、復元済みフレーム数ではない。

| 映像の設定速度 | 640×360の実測速度 | 1920×1080の実測速度（初回） | 1920×1080の実測速度（再測定） |
| --- | --- | --- | --- |
| 3倍速 | 2.99倍 | 3.00倍 | 3.00倍 |
| 4倍速 | 4.00倍 | 4.00倍 | 4.00倍 |
| 8倍速 | 8.00倍 | 8.00倍 | 8.00倍 |
| 12倍速 | 12.00倍 | 11.65倍 | 11.85倍 |
| 16倍速 | 16.00倍 | 9.24倍 | 9.37倍 |

高解像度の再測定では、8倍速の `waiting` は4秒間に2回・合計約20ミリ秒、12倍速では6回・約111ミリ秒、16倍速では87回・約1694ミリ秒だった。16倍速でも先読みは最低約63秒あり、ファイルは最後までローカルに取得済み。今回の16倍速の停滞を外部回線の不足では説明できない。

この環境では32倍速の設定は `NotSupportedError` になった。Chromiumのソースにも上限16倍速が定義されているが、他のブラウザも同じ範囲を受け付けるという保証ではない。

### 音声1倍速・60秒遅れからの回復

| 実験用の制御 | 640×360の回復時間 | 1920×1080の回復時間 |
| --- | --- | --- |
| 現行（最大3倍速） | 32.0秒 | 36.3秒※ |
| 最大8倍速 | 11.5秒 | 11.6秒 |
| 最大12倍速 | 8.7秒 | 9.3秒 |
| 最大16倍速 | 7.4秒 | 16.7秒 |

※高解像度の現行制御はファイルの末尾に近づき、先読みが約3.2秒まで減って終盤の増速も制限された。640×360は最低約127秒の先読みを保っているため、現行制御との比較の主な基準はこちらである。高解像度の高速制御3種類は、いずれも最低約22秒以上を保った。

全試験で、測定中の音声停止・音声速度変更・動画シークは0回。設定を16倍速にすることが最速とは限らず、高解像度では最大8倍速よりも回復に時間がかかった。

音声2倍速・30秒遅れの640×360動画でも確認した。現行制御の回復は15.5秒、最大8倍速は6.4秒、最大12倍速は4.9秒で、音声は2倍速のまま停止せずに進んだ。

機械可読の要約は [video-catch-up-results.json](video-catch-up-results.json)。実験条件と各試験の指標を保存し、詳細なフレームごとのログはベンチマーク実行時に出力する。

## 次の実装案

1. **大きな遅れがある時だけ高速追随を試す。** 初期位置・手動シーク完了後の猶予を守り、小さなずれには現行制御を使う。音声の再生・速度・位置には介入しない。
2. **4→6→8→12倍速のように段階的に試す。** 各段階で約2秒の観測区間を設け、設定値ではなく、内部時計とフレームの実際の進み・遅れの縮まり方を比較する。16倍速を常用せず、検証後に追加の候補とする。
3. **改善しない増速は取り消す。** 速度を上げても実測の進みが増えない、回復が遅くなる、待機時間が増える場合は、直前の有効な段階へ戻す。退避後は一定期間上限を固定し、再増速と待機の反復を防ぐ。単発の短い `waiting` だけで回線不足と判断しない。
4. **先読みの消費も毎回確認する。** 秒数を候補速度で割った残り実時間で評価する。探索開始には余裕を持たせ、先読みが減ったら新しい観測区間の完了を待たずに減速する。現在のバッファ量は将来のデータ到着を保証しない。
5. **追いつく前に減速する。** 残りの遅れと制御更新間隔から増速を制限し、数秒以内の遅れになったら現行の細かな速度調整へ戻す。先行と再加速の往復を防ぐ。
6. **観測できない状況を分ける。** シーク・素材切り替え・音声速度変更では観測窓をリセットする。非表示タブでは探索しない。フレーム通知API非対応では従来の上限を使う。画面共有の可変フレームレートでは静止区間に通知が少なくなるため、通知が来ないことだけでデコード限界と判定しない。
7. **通常時の計算は小さくする。** 高速追随中だけフレームの時刻など数個の数値を収集し、速度判定は1〜2秒ごとに行う。追加のFFmpeg、全動画の事前解析、再エンコード、Canvasへのフレームコピーは不要。詳細な診断ログは引き続き明示的な有効化時だけ出す。

開始条件・観測窓・改善率の閾値・退避期間は、実際の録画と普段のブラウザでも測定して調整する。今回の資料は8倍速や12倍速をすべての端末で保証するものではない。警告は現在の「1秒超のずれが10秒以上継続」を維持する。

## 再現方法

アプリ用の依存関係にPlaywrightを追加する必要はない。別ディレクトリへインストールして、そのモジュールパスとChromium実行ファイルを指定する。

```bash
npm install --prefix /tmp/bbb-video-benchmark playwright
/tmp/bbb-video-benchmark/node_modules/.bin/playwright install chromium
```

同種のテスト素材を生成する例。これはテスト用の新規ファイルを作る操作で、会議のraw素材は使用しない。FFmpegのバージョンや生成素材によって数値は変わる。

```bash
ffmpeg -f lavfi -i testsrc2=size=640x360:rate=10 -t 240 -an \
  -c:v libvpx -deadline realtime -cpu-used 8 -b:v 400k \
  -g 3000 -keyint_min 3000 /tmp/catch-up-360.webm

ffmpeg -f lavfi -i testsrc2=size=1920x1080:rate=30 -t 120 -an \
  -c:v libvpx -deadline realtime -cpu-used 8 -threads 4 -b:v 2500k \
  -g 4000 -keyint_min 4000 /tmp/catch-up-1080.webm
```

生成後は `ffprobe -v error -select_streams v:0 -show_entries packet=pts_time,flags -of csv=p=0 FILE.webm` で `K` のあるパケットを確認する。

リポジトリのルートから実行する。`CHROMIUM` は実行ファイルの実際のパスへ置き換える。

```bash
node scripts/benchmark-video-catch-up.cjs \
  --video /tmp/catch-up-360.webm --browser CHROMIUM \
  --playwright /tmp/bbb-video-benchmark/node_modules/playwright \
  --output /tmp/catch-up-sweep.json

node scripts/benchmark-video-catch-up.cjs \
  --video /tmp/catch-up-360.webm --browser CHROMIUM \
  --playwright /tmp/bbb-video-benchmark/node_modules/playwright \
  --mode recovery --lag 60 --audio-rate 1 \
  --output /tmp/catch-up-recovery.json
```

各試験は別ページで順番に行う。負荷の重い処理を同時に実行せず、同じ条件で再測定する。実際の録画ファイルを使う場合もスクリプトはローカルのHTTPサーバからファイルを読むだけだが、最後までメモリへ取得するため大きな素材には向かない。
